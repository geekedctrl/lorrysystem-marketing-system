# Native Settings and organizations

The native API now owns organizations separately from workspaces. Organization `OWNER` and `ADMIN` can create workspaces without `platform_admin`; the creator receives workspace `ADMIN`. Workspace roles continue to govern product, review, automation and sending actions. Executor ownership and migration controls still require `platform_admin`.

Migration `012_organizations` assigns each existing workspace its own organization. The active platform administrator with the first UUID becomes owner; if none exists, the first workspace `ADMIN` becomes owner. Workspace memberships and roles remain unchanged. Workspaces without either account receive an organization with no owner and require a deliberate administrative recovery before customer management. Migration `013_provider_connections` adds encrypted provider drafts under workspace RLS. Neither migration activates providers or changes automation. New legacy account migration inserts one organization per imported workspace and assigns an owner after importing accounts and memberships.

Native routes provide organization listing/creation, member listing and roles, workspace creation with an idempotency key, workspace profile/status/members, invitation issue/accept, account password/session controls, and connection status. Workspace deactivation is reversible from Organization Settings and does not delete records. Invitation codes are returned once to an authorized administrator for secure sharing; no email is sent. Password changes revoke other sessions. Provider drafts use the existing workspace-bound Fernet credential key, remain disabled and unverified, and are never returned as plaintext. Workers continue to use only their configured environment credentials until a separate calibration and enablement change. The existing sender API retains encrypted secret storage and verification.

The dashboard BFF keeps bearer credentials in its opaque server session, checks CSRF for every mutation, and forwards only allowlisted paths. The native sidebar has organization and workspace selectors plus Settings subnavigation. Product setup, automation preferences/job health and connections are under Settings. The empty account flow creates an organization and workspace in two steps, selects it, and opens product setup. Legacy dashboard routes remain available for rollback.

Local verification uses synthetic accounts, organizations and providers. Run `docker compose --env-file .env -p marketing-rebuild -f compose.backend.yml --profile test run --rm --no-deps --build backend-test` against the dedicated `marketing_rebuild_test` database. Run `.venv/Scripts/python dashboard/scripts/validate_native_frontend.py --browser` for BFF and headless Edge acceptance. The separate `tests.organization_backfill_check` script requires a fresh `marketing_org_backfill_test` database and rejects any other URL. `tests.organization_restricted_check` exercises creation, profile, status and password changes with the restricted API role against the synthetic test database.

The native dashboard still uses process-local sessions. A shared session store remains a release requirement. Provider configuration is environment-owned; this Settings change reports its state but does not create or verify paid provider credentials. No deployment or executor cutover is included.
